# Native app builds

`{{MOBILE_DIR}}` ships up to three ways: as a PWA, as an Android APK, and through TestFlight. This
page is the second and third; the Apple-console side is
[`native-ios-release.md`](./native-ios-release.md), the build-distribution portal testers install
from (if you run one) is [`dist-server-portal.md`](./dist-server-portal.md), and push is [`native-push.md`](./native-push.md).
Per-variable reference lives in `.env.example`; what is here is what that cannot tell you.

**The iOS half needs a Mac and cannot be containerised** — Xcode, CocoaPods and `altool` have no
Linux path, so it is unreachable from Linux dev boxes and CI agents. The Android script is
merely macOS-*shaped*.

## Pin the JDK; the ambient one is the wrong one

`/usr/libexec/java_home` often hands back an old JDK (e.g. Zulu 11) that Gradle rejects. The build
script must force `JAVA_HOME` to the JDK the Android Gradle plugin of your Capacitor version needs
(Homebrew `openjdk@17` or `@21`, per the plugin's requirement) and, if it is not installed, warn
and fall back to the ambient value rather than hide the problem. A wrong JDK fails loudly; a wrong
app id (below) fails quietly in signing and push. Re-check the required JDK whenever Capacitor or
the Gradle plugin is upgraded.

## Native projects: tracked or generated — decide once

Two workable schemes, and the page for your project must say which it is:

- **Tracked** (preferred): `ios/` and `android/` are committed. Manifests, plists, entitlements,
  URL schemes and launcher icons are ordinary versioned files, edited and reviewed like any source.
  `npx cap add <platform>` is then a first-time generator, not a lifecycle step: running it over the
  tracked tree regenerates Capacitor defaults into the working copy, which must not be committed
  blindly. Build junk stays out via the projects' inner `.gitignore`s (Pods, `App/build`,
  `App/public`, the generated `capacitor.config.json`, the archive output folder).
- **Gitignored**: anything that lives only in the native folders — icons, permissions, version
  stamps — is recreated from Capacitor templates whenever `cap add` runs, and no diff reveals it.
  The build scripts must then **re-assert** those settings on every run (ensure icons, ensure
  permissions, ensure plist keys, stamp the version); a new native-only setting belongs in that
  list, not in a one-off manual step.

Two things ride a sync contract either way: the **version stamp** (the package manifest is the
single version source; a stamp script runs at the start of every native build) and the **launcher
icons** (a generation source plus a manual regeneration tool for the next brand change — run it,
review the diff, commit; the commit is the deliverable, not the copy).

## The app id must agree in every place

The bundle/application id is stated in at least: the Capacitor config's `appId`, Android's
`namespace`/`applicationId`, iOS's `PRODUCT_BUNDLE_IDENTIFIER`, and the backend's push app id
(APNs topic, Android push-tap scheme). Once the projects are not regenerated by `cap sync`, editing
only the Capacitor config leaves the others behind. An id already registered with Apple or Play
**cannot be changed for an existing app**, and an id once bound to an Apple record by a first
upload (TestFlight included) is bound for ever — pick the final one before the first upload.

## Version number is a review decision

The manifest `version` is the single source; the stamp script derives three values:

- the **visible** version (iOS `CFBundleShortVersionString`, Android `versionName`) is
  `major.minor` **only**. A patch bump leaves it unchanged, and TestFlight (as the script author
  understands it — verify) does not demand a fresh Beta App Review for a short version it has
  already reviewed; the patch advances only the build number, which is all a re-upload needs. Minor
  and major bumps trigger review (about a day before external testers can install).
- Android `versionCode` is `major*10000 + minor*100 + patch`, because Play rejects a non-increasing
  integer. The arithmetic **caps minor and patch at 99**: `0.1.100` and `0.2.0` collide.
- the iOS build number must increase per upload of the same marketing version — bump the manifest
  version before re-uploading.

## `dev` and `release` name what is inside the bundle, not how it is signed

`dev` is a thin shell whose WebView loads JS over the LAN from your Vite dev server; `release`
packages the production bundle inside. The Capacitor config emits a `server.url` block **only**
when a dev-server env variable is set, so the env of the `cap sync` run decides which of the two a
native project currently is — which is why release scripts `unset` it first (an inherited value
would ship a LAN URL to a tester).

⚠️ An Android "release" produced via `assembleDebug` is a debug-signed APK carrying the production
bundle. State it plainly if that is your state: the channel name is about the bundle, not the
signature, until a store-signed artifact is produced.

## The root `.env` is parsed, never sourced

`. .env` on a file written for docker compose executes part of it: compose's dotenv dialect doesn't
require quoting a value with spaces, so sourcing it as shell word-splits the value and runs the tail
as a command (`APP_TITLE=My Cool App` becomes `Cool: command not found`). Every script goes through one
`load_root_env` helper that reads line by line, skips anything that is not `KEY=value`, strips one layer of quotes
the way compose does, and never evaluates. Anything else needing the root `.env` from a shell owes
the same treatment — `set -a; . .env` is not a safe idiom, and it fails loudly only sometimes.

## The `VITE_*` leak that bakes localhost into a release

The build scripts load the root `.env` (that's where the dev host lives), which exports every dev
`VITE_*` into the process. **Vite gives `process.env` precedence over its own `.env` files**, so a
release `vite build` would silently prefer the dev API URL over the release env file and bake
`localhost` into the APK/IPA. Clear them first (`for v in ${!VITE_@}; do unset "$v"; done`). The
failure mode is a build that succeeds and an app that cannot reach anything. The release env file
is gitignored, so a fresh checkout has only `.env.production.example` — copy and fill it first.

## The release env file is a precondition, not a hope

A missing or half-filled release env file doesn't fail `vite build`; it ships an app pointing at its
fallback host, green the whole way (`[SUCCESS] release APK ready`), and the publish script hands the
portal a broken build. A `require_mobile_release_env` check, called by **every** consumer of that
file (Android release, iOS, PWA build), is the guard. Why it is shaped as it is — each obvious
version is wrong:

- it **parses the way Vite's dotenv does** and judges only the final value per key (last
  assignment wins; an unquoted value ends at its first `#`, so `VAR= # TODO` is *empty*) — a guard
  that parses differently from the build judges values the build never uses;
- it **never exports** what it parses (an exported `VITE_*` outranks the file — the leak above);
- it **classifies the host, not the URL string** (a substring match on `10.` reads
  `api10.example.com` as private);
- a **private LAN address warns rather than fails** — an internal-only stand is legitimate, and
  dev instructions tell people to put a LAN IP in these very variables;
- it **fails closed on a missing file**, deliberately the opposite of `load_root_env`, because the
  root `.env` is optional and a release env file is not.

## Source maps go to the error tracker, and only with a token

The `VITE_*` sweep leaves the monitoring keys (`SENTRY_*`) in place. With the auth token set, the
build emits hidden maps, uploads them and deletes the `.map` files from `dist/` — **before
`cap sync`**, so none ends up in the APK or IPA. Without the token there are no maps and the build
is unchanged. If you use a PWA service-worker plugin, turn its own source maps off: it writes them
*after* the upload plugin has deleted the app's, so `sw.js.map` would ship. Details and SDK pinning:
[`client-monitoring.md`](./client-monitoring.md).

## iOS is asymmetric, and that is not an omission

iOS can't be sideloaded the way an APK can:

- **dev** runs from Xcode on a tethered device and is **never** published; a distribution portal
  has three platform×channel targets, not four, and an empty `ios/dev` is the design.
- **release** archives, uploads the IPA to TestFlight, and publishes only the public **join link**
  to the portal. With the link variable empty the upload still happens and the portal step is
  skipped with a warning — the right path on a first release, when no tester group exists yet.
- **`PUBLISH_ONLY=1` publishes the link without building.** The first release runs in two passes —
  upload, wait for the group to exist, then record its link — and re-running the whole flow would
  send TestFlight a second identical IPA. With it set an empty link becomes an **error**, not a
  warning: there is nothing else the run could have done.

Mechanical traps: build the **`.xcworkspace`**, never the bare `.xcodeproj` (Capacitor manages
native deps through CocoaPods; the bare project fails on unresolved imports); and `xcrun altool`
resolves the API key **by id, from `~/.appstoreconnect/private_keys/`**, not from the path you
configured — the build script copies it there, so pointing the config var at a valid `.p8` isn't
enough on its own. The export-compliance flag (`ITSAppUsesNonExemptEncryption=false`) is
re-asserted each build (idempotent) so the question never appears on upload.
